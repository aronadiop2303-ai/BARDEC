Réessaie dans un instant." sur chaque tentative, comportement attendu depuis le masquage des erreurs brutes (audit sécurité du 16 août) mais sans cause visible. **Cause racine trouvée en base et confirmée en local, pas dans le code de l'app** : la variable d'environnement EAS `EXPO_PUBLIC_SUPABASE_ANON_KEY` (environnement `preview`, celui utilisé par le profil de build `preview`) ne contenait pas uniquement la clé anon — elle contenait les 3 variables (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_MAP_TOKEN`) collées bout à bout sans retour à la ligne, résultat probable d'un copier-coller du `.env` entier dans le mauvais champ lors de la configuration EAS du 15 août. L'app embarquait donc cette chaîne de 345 caractères comme header `apikey` — non vide (donc `isSupabaseConfigured` passait), mais pas un JWT valide → `401 UNAUTHORIZED_INVALID_API_KEY` ("Not a JWT") côté Supabase sur **toutes** les requêtes de l'APK (signup, produits, nearby_shops), pas seulement l'inscription. Confirmé via `edge_logs` Supabase (hint explicite "Not a JWT") et via `eas env:pull` (valeur brute corrompue lisible directement dans le fichier, pas un artefact d'affichage terminal). Un rebuild sans corriger la variable (build `a82f92f7`) a reproduit exactement la même erreur, écartant l'hypothèse d'un build figé/en cache. Un `expo export` local avec des valeurs propres a confirmé que l'inlining Babel/Metro des `EXPO_PUBLIC_*` fonctionne normalement — le problème était uniquement la valeur stockée côté EAS, pas le code. **Corrigé** : valeur réécrite via `eas env:set` (JWT propre uniquement), nouveau build (`93678fd0`) lancé et installé — inscription confirmée fonctionnelle par Arona, `edge_logs` ne montre plus aucun `401`/`Not a JWT` depuis le fix (dernière occurrence 14:37:47, requêtes suivantes toutes en 200).
