## 🔴 BLOQUANT

- [x] Produits ajoutés par le vendeur n'apparaissent pas dans l'accueil/liste produits publique — **cause racine trouvée et corrigée** : `handleAddProduct` (vendor-dashboard.tsx) basculait silencieusement en branche locale/démo (`_imported:true`, aucun insert Supabase) dès que `user` du contexte était faux à l'instant du tap, sans jamais toucher la base ni afficher d'erreur. Guard changé pour ne dépendre que de `isSupabaseConfigured`/`supabase` ; l'UUID réel est toujours résolu via `supabase.auth.getUser()`, avec message "Session expirée" explicite si absent. À confirmer sur téléphone.
- [x] Produits avec une catégorie assignée invisibles nulle part — picker de catégorie (CATEGORIES partagé avec l'accueil) posé lors d'une session précédente ; combiné au fix ci-dessus, l'insert atteint désormais réellement la base avec un `category` valide. À confirmer sur téléphone.
  - [ ] Point lié : l'import CSV en masse (vendor-dashboard.tsx) a le même mismatch de taxonomie catégorie (texte libre non validé) — non corrigé par le picker du formulaire manuel, à traiter dans une session séparée
- [x] Image produit ne s'affiche pas dans "Mes produits" côté vendeur — même cause racine que l'item ImagePicker ci-dessous (upload échouait silencieusement, produit enregistré sans image)
- [x] Commande passée par le buyer n'apparaît pas dans sa liste de commandes — **même cause racine** que le bug produit ci-dessus, trouvée dans `checkout.tsx` : le bloc d'insert vers `orders` était sauté silencieusement si `user` était faux, et le flow avançait quand même à l'étape "confirmation" comme si la commande avait réussi. Même correctif appliqué. Bug identique corrigé en prime dans `profile.tsx` (upload avatar) et `app/proximity/cart.tsx` (commande boutique de quartier), qui avaient exactement le même défaut. À confirmer sur téléphone.
- [x] Statut de commande mis à jour par le vendeur n'apparaît pas côté commande réelle (reproduit après le fix RLS : le vendeur peut changer le statut mais ça ne se reflète pas ailleurs) — **cause racine trouvée** : `switchDemoRole` (AuthContext.tsx), le sélecteur de rôle utilisé pour tester plusieurs rôles depuis un même compte, remplaçait `user` par un faux profil `DEMO_USERS` (id `"u1"`…) **même en mode Supabase réel**. La session Supabase Auth réelle (`auth.uid()`) ne change pas, donc en prévisualisant "ACHETEUR" depuis un compte vendeur réel, l'onglet Commandes interrogeait `orders_customer` avec l'UUID du vendeur (propriétaire d'aucune commande) — d'où l'impression que la mise à jour de statut "ne se reflète nulle part", alors que ce n'était juste pas le bon compte. Corrigé : en mode réel, le switcher ne modifie plus que le champ `role` sur l'utilisateur authentifié réel (id/email inchangés) ; c'est désormais une prévisualisation UI uniquement, RLS reste appliqué selon le vrai rôle en base. À confirmer sur téléphone avec deux vrais comptes (vendeur + acheteur), pas via le switcher.
- [x] Admin ne voit aucune donnée réelle (dashboard, utilisateurs, vendeurs, commandes semblent être des données de test) — **partiellement corrigé**. `admin.tsx` n'avait strictement aucune intégration Supabase (pas un bug, une fonctionnalité jamais câblée). Onglets **Dashboard/Utilisateurs/Vendeurs en attente/Commandes** branchés sur les vraies tables `users`/`orders` (policies `users_admin`/`orders_admin` déjà en place, confirmées). Bouton "Approuver" un vendeur écrit réellement `users.is_approved = true`.
  - [x] Point découvert : une vraie table `vendors` existe en base avec exactement les colonnes KYC qu'utilisait l'ancien UI mocké (`kyc_status`, `documents`, `country`, `verified`, `response_rate`, `total_sales`, `avg_rating`) — RLS était activé **sans aucune policy**, donc illisible par personne, même ADMIN. Policies ajoutées le 14 août (voir plus bas). L'onglet Vendeurs admin utilise toujours `users` en version simplifiée pour l'instant — brancher les champs KYC détaillés sur `vendors` reste un chantier à part (l'accès en base n'est plus le blocage).
  - [ ] Restent mock (non câblés, hors périmètre de cette session) : Paiements, Litiges (`disputes` a maintenant ses policies RLS mais l'UI admin.tsx reste mockée), Clés API/MCP, Paramètres, et le graphique B2B vs B2C du Dashboard.
- [x] Erreur de navigation "REPLACE" sur la route vendor-dashboard (log dev) — `router.replace()` imperatif dans un `useEffect` remplacé par `<Redirect>` déclaratif (index.tsx), le pattern documenté Expo Router pour éviter de naviguer avant que le navigator soit prêt
- [x] Crash du sélecteur de photo Android : ExponentImagePicker.launchImageLibraryAsync renvoie une URI content:// que le code ne gère pas ("Uri lacks 'file' scheme") — touche upload photo profil et ajout photo boutique de quartier. **Cause confirmée** (issue GitHub expo/expo#25098/#25315/#25097 : combo `allowsMultipleSelection` + `quality < 1`) et corrigée (`quality: 1` sur le picker produit vendeur), + nouveau helper `lib/imageUpload.ts` (`readLocalImageBytes`) qui copie les URI `content://` vers un fichier local avant lecture, appliqué aux 4 pipelines d'upload (photo produit, avatar, photo boutique de quartier x2). Le pipeline "ajout produit boutique de quartier" abandonnait aussi silencieusement l'upload pour toute URI non-`file://` — corrigé au passage.

- [x] Policies RLS ajoutées sur `vendors`/`disputes`/`reviews`/`audit_logs` (validées par Arona, appliquées le 14 août via migration `add_vendors_disputes_reviews_audit_logs_policies`). `reviews` en lecture publique + auteur gère les siens ; `vendors`/`disputes`/`audit_logs` en self-scope + admin.
- [ ] **[Découvert 14 août]** Table `public.spatial_ref_sys` (table système PostGIS) a Row Level Security **désactivé** en production — signalé en `ERROR` par l'auditeur sécurité Supabase. **Non corrigeable depuis le SQL Editor / l'API du projet** : `ALTER TABLE` échoue avec `must be owner of table spatial_ref_sys`, la table appartenant au rôle interne `supabase_admin` (celui qui installe l'extension PostGIS), pas à `postgres`. Limitation connue des projets Supabase+PostGIS — seul le support Supabase peut l'appliquer côté infra. Risque réel faible (aucune donnée utilisateur, juste des définitions de systèmes de coordonnées). Laissé tel quel, à rouvrir seulement si tu veux contacter le support Supabase pour ça.

- [x] **[Découvert 14 août]** Avis produits (`reviews`) : le code (lecture dans `product/[id].tsx` et écriture dans `orders.tsx`) référençait une colonne `verified_purchase` qui n'existe pas — la vraie colonne s'appelle `verified`. Masqué jusqu'ici par le blocage RLS total sur `reviews` (voir policy proposée en fin de session), mais aurait fait échouer chaque tentative de publier un avis une fois la policy ajoutée. Corrigé dans les deux fichiers.

  - La fonction edge `omni-agent` **est bien déployée** (contrairement à l'hypothèse de départ) — mais le dossier `supabase/edge-functions/omni-agent/` du repo ne correspondait **pas du tout** à ce qui tournait réellement en prod (un brouillon plus ancien : streaming SSE, table `omni_memory` avec des colonnes `key`/`value` qui n'existent pas, URL MCP de secours pointant vers un **autre projet Supabase**). Le code lève explicitement `"ANTHROPIC_API_KEY manquant dans les secrets de la fonction."` dans ce cas précis.
  - **Bloqué sur toi** : `ANTHROPIC_API_KEY` doit être ajouté dans **Supabase Dashboard → Edge Functions → omni-agent → Secrets** — c'est une clé Anthropic réelle, je ne peux ni la deviner ni la générer. Donne-la moi et je peux te confirmer une fois que ça répond, ou ajoute-la toi-même directement dans le dashboard.
  - Deux autres secrets manquent aussi (`MCP_SERVER_URL`, `OMNI_MCP_API_KEY`) mais ne bloquent pas les réponses de base — seulement les capacités "outils" (chercher un produit, vérifier une commande). Valeurs exactes données dans `supabase/edge-functions/omni-agent/README.md` (déjà en base : `MCP_SERVER_URL` = URL de la fonction `mcp-server` du même projet ; `OMNI_MCP_API_KEY` = valeur de la clé `omni-agent-v0.1` déjà présente dans la table `api_keys`, jamais utilisée jusqu'ici — `last_used` est `null`).
